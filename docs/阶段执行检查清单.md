# 阶段执行检查清单

## 使用规则
- 机器可读阶段契约以 `stage-manifests/*.yaml` 为唯一真源；本清单负责解释规则，不再单独维护另一套代码判定口径。
- 统一阶段检查入口为 `scripts/check-stage.ps1` / `scripts/check-stage.sh`；总控与执行脚本应优先消费 `stage-status` JSON，而不是只看文件是否存在。
- AI 默认先读 `docs/AI执行最小规则.md`，再进入当前阶段直接相关的正式输入。
- 每次进入下一阶段前，先检查上一阶段产出文件是否已生成并保存。
- 产出内容为空、仅模板未填写、或结论没有来源时，视为未完成。
- 不确定的需求、规则、环境、账号、URL、接口字段必须标记为“待确认”。
- 只要真实接口可访问，接口分析、接口用例、API 自动化和系统报告必须优先依据实测接口行为；接口文档只作为差异对照来源。
- 有接口文档但与真实接口不一致时，必须记录“文档与实际接口差异/待确认”；未确认以文档为准前，不得把文档字段作为 smoke 阻断硬断言。
- 没有接口文档时，必须先形成实测接口基线，再设计接口用例和自动化断言；不得写“按接口文档应返回”。
- 未实际执行的自动化、性能、安全测试必须写“未执行”，不得写成通过。
- 执行任何自动化或专项测试前，必须先做被测服务连通性检查；若被测地址连接被拒绝、超时或 DNS/网络不可达，后续 API、UI、性能、安全测试均不得继续执行，只能记录“未执行”和失败原因。
- 服务预检或 API smoke 中若发现服务级连接失败（如 `ConnectionRefusedError`、`WinError 10061`、`ERR_CONNECTION_REFUSED`）、读超时或真实认证不可用，必须立即停止后续 UI、性能、安全执行；API smoke 已通过后的 API 全量局部接口失败或超时，记录为 API 缺陷/稳定性风险，允许 UI 按独立门禁执行，但停止性能、安全等后置专项。
- 性能测试必须先确认 JMeter 已安装或 `JMETER_BIN` 已配置；未配置时性能测试写“未执行”，不得尝试压测。
- 安全测试必须先确认 Docker/ZAP 或本地 ZAP 执行入口已配置；未配置时 ZAP 扫描写“未执行”，不得尝试扫描。
- 未确认测试目标可达、测试工具就绪、压测/扫描配置完整时，不允许为“走完整流程”而强行执行后续专项。
- 所有测试用例表必须包含“序号”列，并放在“用例编号”前；序号必须从 1 连续递增。
- 自动化执行前必须先生成覆盖矩阵；覆盖矩阵需逐条映射评审版用例到脚本、执行层级和状态。
- 若覆盖矩阵显示存在“自动化但未实现”的用例，只能执行 partial/smoke/已实现范围，不得宣称完整自动化完成。
- 系统测试报告必须建立证据索引；关键统计缺少来源文件或原始结果路径时，必须标记“证据不完整”。
- 系统测试报告发现覆盖矩阵、执行报告、缺陷清单统计冲突时，必须列入待确认，不得强行写通过。
- 系统测试报告不得明文暴露密码、token、cookie 或可复用会话信息。
- 系统测试报告和测试知识沉淀采用"增量追加"模式：每个测试专项（API / UI / 性能 / 安全）完成后，必须立即增量更新 `docs/reports/系统测试报告.md` 和 `docs/knowledge/` 对应文件，不得等待所有专项完成才统一生成。
- 系统测试报告中尚未执行的专项必须标注"未执行"并说明原因；后续专项完成时追加到同一报告中。
- 每次增量更新系统测试报告后，必须同步更新 `docs/test-runs/YYYYMMDD-HHMMSS/批次摘要.md`。
- 每个专项完成后立即沉淀该专项的经验和模式到 `docs/knowledge/`，不等所有专项完成。
- 测试知识沉淀不得修改历史报告和执行结果；证据不足的信息必须写“待确认”，不得沉淀为确定结论。
- 每轮测试产出必须按测试时间归档到 `docs/test-runs/YYYYMMDD-HHMMSS/`；阶段报告、覆盖矩阵、缺陷清单和原始自动化报告均需进入本轮时间目录。
- 每轮归档还必须包含 `docs/test-runs/YYYYMMDD-HHMMSS/stage-status/`，保存 `stage_id`、`status`、`inputs_checked`、`gates_checked`、`outputs_written`、`next_decision` 等统一状态字段。
- `check-stage` 返回 `completed` 只表示阶段产物、未执行说明或结果已按契约落盘，不等于该专项真实执行通过；真实是否执行和是否通过必须看专项正式报告中的执行状态和下一步决策。
- `docs/reports/` 和 `docs/defects/` 可保留最新版本，但历史追溯必须以 `docs/test-runs/` 下的时间目录为准。
- AI 读取时默认先看轻量索引：`docs/knowledge/README.md`、本轮 `docs/test-runs/YYYYMMDD-HHMMSS/批次摘要.md`、覆盖矩阵、专项报告；只有索引无法回答问题时，才展开原始结果或整目录。
- 系统测试报告和知识沉淀阶段不得把 `docs/reports/`、`tests/` 的整目录扫描当成默认动作；必须优先使用本轮批次摘要和最新正式产物。
- `批次摘要.md` 负责当前批次事实快照，`系统测试报告.md` 负责全局判断与证据索引，`docs/knowledge/*.md` 负责可复用知识；三类文档不得默认互相整段重写。
- `docs/reports/*阶段细化方案.md` 和其他重构说明文档默认为参考资料，只在当前 stage/skill 未覆盖细节时按需读取。
- 静态校验脚本或收集用例不得污染正式原始报告；pytest collect-only 必须覆盖默认 addopts 或输出到临时目录。
- 执行类阶段不得只跑脚本；必须先跑冒烟，再基于结果分析决定继续、复测、补资料、降级或停止。
- 每个执行类阶段必须输出“下一步决策”，并说明为什么做这个决策。
- API full 失败进入缺陷闭环后，修复接回流程必须按 smoke、failed-retest、API full 的顺序恢复；定向复测通过不能替代 API full。
- API full 失败项必须全部进入缺陷清单；文档与实际接口不一致登记为接口契约/文档一致性缺陷，不能因“待确认”而不输出缺陷。

## 环境与工具门禁
| 门禁项 | 检查方式 | 失败处理 |
|--------|----------|----------|
| 被测服务连通性 | 对被测地址执行 HTTP GET/HEAD 或等价探测 | API、UI、性能、安全均写“未执行”，停止后续执行 |
| API 基础连通性 | 服务预检和 API smoke 无服务级连接失败，登录接口和核心只读接口可用 | 若服务预检或 API smoke 连接被拒绝/超时/认证不可用，停止 UI、性能、安全；若仅 API 全量局部接口失败，允许 UI 独立执行 |
| API 断言口径 | 已区分实测接口基线、文档差异核对、已确认契约断言 | 未确认文档契约只能写待确认或差异核对，不作为 smoke 阻断 |
| JMeter 配置 | `jmeter -v` 可用，或 `JMETER_BIN` 指向可执行文件 | 性能测试写“未执行”，不启动压测 |
| ZAP 配置 | Docker 可用并能运行 ZAP 镜像，或本地 ZAP 执行入口已配置 | ZAP 扫描写“未执行”，不启动扫描 |
| 压测参数 | 并发数、持续时间、目标接口、数据策略已确认 | 性能测试写“待确认/未执行” |
| 安全扫描范围 | 目标、账号、主动/被动扫描边界已确认 | 安全测试写“待确认/未执行” |

## 测试执行规则门禁（禁止猜测）
| 规则编号 | 规则描述 | 检查方式 | 失败处理 |
|----------|----------|----------|----------|
| TR-001 | 必须先通过浏览器Network或API探测确认真实接口，禁止基于原型文档猜测接口路径 | 需求分析阶段必须列出每个声明接口的HTTP验证结果（状态码、响应结构） | 接口未验证则需求分析不通过，标注"待确认" |
| TR-002 | 数据一致性测试必须直接使用系统返回的统计接口数据，禁止自行通过基础CRUD接口聚合计算 | 数据一致性测试脚本必须调用系统统计接口（如 /crm/goalManage/list），而非自行聚合 | 测试结果无效，重新编写测试脚本 |
| TR-003 | 统计口径（时间范围、用户范围、数据定义）必须与系统保持一致，禁止假设统计逻辑 | 对比系统展示数据与测试统计数据，确认口径一致 | 口径不一致时记录差异原因，不修改断言 |
| TR-004 | 接口字段名必须通过实际返回值确认，禁止基于文档或经验推断字段名 | 接口测试脚本中使用的字段名必须来自接口实际返回值 | 字段名错误导致测试失败，修复后重新执行 |
| TR-005 | 发现数据不一致时，必须先对比系统接口返回值与测试计算值，分析差异原因，而非直接修改断言 | 数据不一致时输出系统值与测试值的对比，分析差异原因 | 差异原因未分析前，不修改断言逻辑 |

## 冒烟后自适应决策门禁
| 决策状态 | 触发条件 | 后续动作 | 必须记录 |
|----------|----------|----------|----------|
| continue | 冒烟通过，指标达标或风险可接受 | 执行下一层级或下一专项 | 通过证据、继续范围、后续影响 |
| retest | 冒烟结果疑似偶发、环境波动、数据不足或与历史不一致 | 原条件或缩小范围复测 | 复测目的、复测范围、判定标准 |
| collect-evidence | 已发现问题但缺少根因证据 | 暂停加深测试，补日志/监控/数据/配置 | 缺失证据、责任边界、补充方式 |
| downgrade | 全量执行条件不足但可安全执行子集 | 降级执行 smoke/partial/readonly/semi-auto | 降级原因、执行子集、未执行范围 |
| stop | 服务不可达、连接级失败、认证阻断、授权不足、性能/安全风险不可接受 | 停止当前或后续专项 | 阻断证据、影响范围、未执行项 |
| handoff | 缺陷需研发/环境/产品确认或修复 | 不修复，只移交证据和复测建议 | 缺陷证据、影响、复测条件 |

## API 复测接回规则
| 步骤 | 执行入口 | 通过条件 | 不通过处理 |
|------|----------|----------|------------|
| smoke 复核 | `pwsh -File scripts/run-api-tests.ps1 -Mode smoke` | 服务连通、真实认证、核心只读接口通过 | stop/handoff，停止后置专项 |
| 失败项定向复测 | `pwsh -File scripts/run-api-tests.ps1 -Mode failed-retest` | 当前 `retest` 标记失败项全部通过 | handoff，更新缺陷证据和复测状态 |
| API full 回归 | `pwsh -File scripts/run-api-tests.ps1 -Mode full` | 自动化候选按计划执行且无失败 | continue，恢复性能、安全门禁 |
| 单项定位 | `pwsh -File scripts/run-api-tests.ps1 -Mode failed-retest -PytestKeyword "test_name"` | 目标用例通过并证据充足 | 仅用于定位或补证据，不作为阶段恢复依据 |

## 各专项冒烟后判断
| 专项 | 冒烟目标 | 通过后 | 不通过后 |
|------|----------|--------|----------|
| API | 服务连通、认证、核心只读接口 | 继续 readonly/security/write 层级，并允许 UI/性能按门禁继续 | 连接级失败或真实认证不可用则 stop；文档差异或非阻断业务失败不得直接阻断 UI |
| API 断言口径 | 实测行为、文档差异和已确认契约已分层 | 可将已确认契约失败登记缺陷；未确认差异进入待确认 | 未确认文档差异不得直接阻断；断言口径错误进入自动化维护 |
| UI | 登录、首页、一级菜单、核心页面可达 | 继续 readonly/semi-auto/compatibility | 基础阻断则 downgrade 或 stop；不得宣称 full-ui |
| 性能 | 小并发 smoke、错误率、P95/P99、恢复 smoke | 指标达标才讨论加压或综合场景 | 未达标默认 collect-evidence/retest，不直接加压 |
| 安全 | 授权、认证上下文、目标稳定性、被动/基线安全检查 | 在授权范围内继续 ZAP | 授权不足或目标不稳定则 stop/downgrade |

## 自动化覆盖门禁
| 门禁项 | 检查方式 | 失败处理 |
|--------|----------|----------|
| API 覆盖矩阵 | `docs/test-runs/YYYYMMDD-HHMMSS/reports/API自动化覆盖矩阵.md` 存在且与接口评审版用例逐条对应 | 不执行 API 自动化，只输出待确认 |
| UI 覆盖矩阵 | `docs/test-runs/YYYYMMDD-HHMMSS/reports/UI自动化覆盖矩阵.md` 存在且与功能评审版用例逐条对应 | 不执行 UI 自动化，只输出待确认 |
| 自动化范围一致性 | 评审版“自动化”用例均有脚本或明确“未实现/阻塞” | 只能执行 partial，不得写完整执行 |
| 写操作回滚 | write-regression 用例有测试数据和清理策略 | 写操作不执行，只能 semi-auto |

## 自动化执行层级
| 层级 | 执行内容 | 适用专项 |
|------|----------|----------|
| smoke | 最小核心链路和页面可达性 | API/UI |
| readonly-regression | 不改数据的列表、筛选、详情、导出响应 | API/UI |
| semi-auto | 写操作入口、弹窗、必填校验，不提交 | UI |
| write-regression | 真实新增、编辑、删除、处理、同步、改密 | API/UI，需回滚 |
| compatibility | 多浏览器兼容性 | UI |
| performance | JMeter 性能场景 | 性能 |
| security | ZAP 和安全断言 | 安全 |

## 统一输出格式
每个阶段的阶段性回复和落盘报告必须包含：
1. 当前阶段
2. 输入文件
3. 产出文件
4. 正文/核心内容
5. 执行结论
6. 风险与待确认项
7. 下一步建议

补充要求：
- 正文/核心内容必须位于执行结论、风险与待确认项、下一步建议之前。
- 执行结论、风险与待确认项、下一步建议必须作为文档收尾部分。
- 后续所有阶段产出和测试时间归档副本均需遵守该顺序。
- 执行类阶段的正文/核心内容必须包含冒烟结果、结果分析和下一步决策。
