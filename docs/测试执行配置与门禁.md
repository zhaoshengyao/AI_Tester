## 3. 连接失败识别
出现以下任一现象时，判定为服务级连接失败：
- `ConnectionRefusedError`
- `WinError 10061`
- `ERR_CONNECTION_REFUSED`
- `actively refused`
- 连接被拒绝、拒绝连接、连接超时、网络不可达

## 5. 自适应执行配置
本配置的目标是复用测试过程，而不是复用某一次测试结果。任何被测系统接入后，都按以下闭环执行：

1. 门禁检查：确认上一阶段产物、覆盖矩阵、服务连通、工具配置、授权范围。
2. 冒烟执行：先执行最小安全范围，不直接跑全量、压测或主动扫描。
3. 结果分析：基于真实日志、报告、指标和原始结果判断风险。
4. 下一步决策：由 AI 根据证据选择 continue、retest、collect-evidence、downgrade、stop 或 handoff。
5. 执行或停止：只执行被决策允许的范围，未执行内容必须落盘。
6. 配置沉淀：把本轮发现的通用门禁、脚本问题、工具问题和决策规则写回配置或知识库。

## 6. 决策状态
| 状态 | 使用场景 | 示例 |
|------|----------|------|
| continue | 冒烟通过，风险可接受 | API smoke 通过后继续只读回归 |
| retest | 结果可能偶发或证据不足 | UI 偶发超时，缩小范围复跑一次 |
| collect-evidence | 发现问题但缺少定位证据 | 性能 P95 超阈值，补后端日志和慢 SQL |
| downgrade | 全量条件不足但可安全执行子集 | 写操作无回滚，只执行 semi-auto |
| stop | 连接失败、授权不足或风险不可接受 | API 连接被拒绝，停止后续 UI/性能/安全 |
| handoff | 问题需外部确认或修复 | 缺陷移交研发，测试只给证据和复测条件 |

## 7. 各专项自适应规则
| 专项 | 冒烟后继续条件 | 不继续时默认动作 |
|------|----------------|------------------|
| API | 服务连通、真实认证可用、核心接口稳定 | 连接级失败或真实认证不可用 stop；文档差异和非阻断业务失败按缺陷和证据判断 retest/collect-evidence/handoff |
| UI | 登录、首页、一级菜单和核心页面可达 | 基础阻断 stop/downgrade；只跑已实现范围不得宣称 full-ui |
| 性能 | 小并发 smoke 达标，压测后恢复 smoke 通过 | 未达标默认 collect-evidence 或 retest，不直接加压 |
| 安全 | 授权范围、认证上下文、目标稳定性满足 | 授权不足或目标不稳定 stop/downgrade |

## 8. API 缺陷闭环与复测配置
API full 失败后，测试侧进入缺陷闭环与复测准备，不修复后端。恢复后置专项必须按以下顺序：

1. 缺陷移交：输出失败项、证据路径、影响范围和复测条件。
2. smoke 复核：执行 `pwsh -File scripts/run-api-tests.ps1 -Mode smoke`，确认服务连通、真实认证和核心只读接口。
3. 失败项定向复测：执行 `pwsh -File scripts/run-api-tests.ps1 -Mode failed-retest`，只跑当前标记为 `retest` 的失败项。
4. API full 回归：定向复测通过后执行 `pwsh -File scripts/run-api-tests.ps1 -Mode full`。
5. 门禁恢复：只有 API full 通过，才允许恢复性能和安全专项。

如只需定位单个问题，可使用 `-PytestKeyword "test_name"` 叠加过滤；该能力只能用于定位和补证据，不能替代 API full 回归。

API full 中的失败项必须全部进入缺陷清单。文档与实际接口不一致、接口契约不清、路由/方法不一致，不作为“等待确认后再登记”的理由，而是登记为接口契约/文档一致性缺陷；后续关闭方式可以是修实现、修文档、改契约或调整用例，但必须有处理证据和复测结果。
