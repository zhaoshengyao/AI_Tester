## 1. 配置目标
这份配置用于沉淀“测试怎么做、为什么这么做、做到哪一步该怎么判断下一步”，而不是保存某一次系统的测试结果。

目标是让本项目配置在以下场景仍可复用：
- 当前电脑继续测试当前系统。
- 复制配置到其他电脑后测试同一个系统。
- 复制配置到其他项目后测试任意系统。
- 换一个 AI 模型后仍按同一流程读取、执行、判断和沉淀。

## 2. 通用执行闭环
所有执行类阶段统一按以下闭环执行：

| 步骤 | 要做什么 | 为什么做 | 产物 |
|------|----------|----------|------|
| 1. 门禁检查 | 检查输入、上一阶段产物、服务连通、工具、授权、覆盖矩阵 | 防止环境没通或资料不足时强行执行 | 门禁结论、未执行范围 |
| 2. 冒烟执行 | 只跑最小安全闭环 | 用低成本确认系统是否值得继续深入 | smoke 结果、原始报告 |
| 3. 结果分析 | 分析错误、超时、失败、覆盖缺口和证据完整性 | 让下一步不是拍脑袋，而是基于证据 | 分析表、缺陷/风险 |
| 4. 下一步决策 | 选择 continue/retest/collect-evidence/downgrade/stop/handoff | 明确为什么继续或停止 | 下一步决策 |
| 5. 执行或停止 | 只执行被允许的范围 | 控制风险和测试成本 | 专项报告、缺陷清单 |
| 6. 沉淀配置 | 把通用规则、工具问题、复测条件、证据缺口写回配置/知识库 | 下次可复用，不重复踩坑 | 知识库、配置更新 |

## 3. 决策状态
| 状态 | 判断条件 | 行动 |
|------|----------|------|
| continue | 冒烟通过，结果稳定，风险可接受 | 继续下一层级或下一专项 |
| retest | 疑似偶发、数据不足、环境波动或与历史不一致 | 原条件或缩小范围复测 |
| collect-evidence | 问题明确但根因证据不足 | 暂停加深测试，补充日志、监控、数据或配置 |
| downgrade | 全量执行条件不足但可以安全跑子集 | 降级执行 smoke/partial/readonly/semi-auto |
| stop | 服务不可用、连接级失败、授权不足、风险不可接受 | 停止当前或后续专项 |
| handoff | 需要研发/环境/产品确认或修复 | 测试只交付证据、影响和复测条件 |

## 4. API 自动化流程
| 阶段 | 做什么 | 为什么 |
|------|--------|--------|
| 覆盖矩阵 | 评审版接口用例逐条映射脚本和状态 | 防止只跑已有脚本却漏用例 |
| API smoke | 登录/认证、服务连通、核心只读接口 | 判断系统后端是否值得继续 |
| 结果分析 | 区分连接失败、认证失败、业务失败、已确认契约不一致、文档差异待确认 | 决定是否阻断 UI/性能/安全 |
| 下一步 | continue/retest/collect-evidence/downgrade/stop/handoff | 让后续动作有证据依据 |

API 连接级失败必须 stop，后续 UI、嵌入式、性能、安全均未执行。

## 5. UI 自动化流程
| 阶段 | 做什么 | 为什么 |
|------|--------|--------|
| 覆盖矩阵 | 功能评审版用例逐条映射页面脚本 | 对齐“要测什么”和“实际跑什么” |
| UI smoke | 登录页、首页、一级菜单、核心页面可达 | 快速发现基础页面阻断 |
| 分层执行 | readonly、semi-auto、compatibility、write-regression | 控制数据污染和执行风险 |
| 下一步 | 根据失败截图、trace、覆盖缺口决定 | 避免只跑 4 条用例就声称 UI 完成 |

UI full 只能在覆盖矩阵中所有可自动化用例均实现并执行后声明。

## 6. 性能测试流程
| 阶段 | 做什么 | 为什么 |
|------|--------|--------|
| 参数门禁 | 确认 JMeter、授权、并发、持续时间、目标接口 | 防止没配置好就压测 |
| 性能 smoke | 小并发、短时长、核心接口 | 用低风险方式判断性能基本面 |
| 结果分析 | 分析错误率、P95/P99、超时类型、吞吐、恢复 smoke | 决定继续加压还是补证据 |
| 下一步 | 达标才考虑综合场景；不达标默认 retest/collect-evidence | 避免在明显失败时直接上 50 并发 |

性能 smoke 不达标时，AI 必须先判断：
- 是否需要单场景复测。
- 是否需要补充后端日志、慢 SQL、资源监控、数据规模。
- 是否应停止 50 并发或安全扫描。

## 7. 安全测试流程
| 阶段 | 做什么 | 为什么 |
|------|--------|--------|
| 授权门禁 | 确认目标、账号、主动/被动扫描边界 | 防止越权和误伤 |
| 安全基线 | 先做低风险被动/基线检查 | 确认目标稳定性和认证上下文 |
| ZAP 扫描 | 在授权范围内执行 | 形成可追溯证据 |
| 下一步 | 根据漏洞等级、误报、目标稳定性决策 | 控制主动扫描风险 |

性能未完成或目标不稳定时，安全测试不得直接主动扫描。

## 8. 嵌入式 protocol-cloud 流程
| 阶段 | 做什么 | 为什么 |
|------|--------|--------|
| 门禁 | 协议文档、设备身份、上报样例、平台查询链路 | 端云联调依赖这些基础条件 |
| 冒烟 | 正常报文上报到平台可查 | 验证最小链路 |
| 分析 | 比对协议、API、UI 展示一致性 | 定位协议/后端/UI/环境归属 |
| 下一步 | 根据链路是否完整决定继续或补资料 | 第一版只做 protocol-cloud，不扩展硬件专项 |

## 9. 系统报告与知识沉淀
- 系统测试报告汇总所有专项的执行结果、未执行原因、下一步决策和证据索引。
- 知识沉淀只沉淀可复用规则，不把一次性结果当成通用结论。
- 每次流程发现新的通用规则，优先写入配置或知识库，避免下一轮重复沟通。

## 10. 跨环境迁移规则
| 项目 | 迁移要求 |
|------|----------|
| 被测地址 | 通过用户输入、环境变量或配置文件提供，不写死 |
| 账号密码 | 账号可记录，密码必须通过环境变量或安全输入，不明文入报告 |
| 工具路径 | JMeter/ZAP/浏览器/Python/Node 均允许环境变量覆盖 |
| 测试数据 | 必须重新确认数据规模、回滚策略和权限 |
| 历史知识 | 只能作为参考，必须与当前实现重新比对 |
| 输出归档 | 仍按 `docs/test-runs/YYYYMMDD-HHMMSS/` 区分测试批次 |

## 执行结论
- 已定义可迁移的测试流程配置：门禁检查、冒烟执行、结果分析、下一步决策、执行或停止、配置沉淀。
- API、UI、嵌入式、性能、安全均必须在冒烟后由 AI 基于真实结果判断下一步。
- 性能测试不再默认“冒烟后继续加压”；未达标时默认先判断复测或补充证据。

## 风险与待确认项
- 待确认：迁移到其他项目时，被测系统的工具链和授权边界。
- 待确认：各系统自己的性能阈值、安全扫描边界和写操作回滚策略。
- 风险：如果直接运行脚本而不读取本配置，仍可能绕过冒烟后决策。

## 下一步建议
- 后续优化 skill 和脚本时，优先补“下一步决策”和“证据缺口”字段。
- 每轮测试完成后，把可复用规则进入 `docs/knowledge/`，把流程规则进入本配置或 `AGENTS.md`。
