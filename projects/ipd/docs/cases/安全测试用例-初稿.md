# IPD 管理系统 安全测试用例（初稿）

> **说明**: 共 28 条（测试计划预估 28）。编号前缀 `SEC-`。分为 5 组：
> - **AUTH 未授权 18 条**（P1，每组 API 18×1 = 18）
> - **JWT 篡改/过期 3 条**（P1，认证核心）
> - **R4 水平越权合规判定 1 条**（P0，高风险专项）
> - **SQL 注入冒烟 5 条**（P1，最小 payload 集合）
> - **XSS 冒烟 1 条**（P2，semi-auto 不实际提交）
>
> 前置条件：自定义安全扫描器入口已配置（`tests/security/` 下存在脚本）；**未配置则降级为基线冒烟手工断言，写"未执行深度扫描：扫描器入口未配置"（AGENTS.md 自动化规则）。**

| 序号 | 用例编号 | 分组 | 目标 | 优先级 | 场景 | 测试步骤 | 预期结果（通过门槛） | 失败说明 → 登记缺陷级别 |
|------|----------|------|------|--------|------|----------|---------------------|-------------------------|
| 1-18 | SEC-UNAUTH-001 ~ SEC-UNAUTH-018 | AUTH 未授权 | 18 条 ✅ GET API | P1（18 条） | 每接口 1 条 | 对 18 条可用 GET API（auth/code、user/profile、menu/getRouters、dict/type/sys_yes_no、dict/common_status、user/list、dashboard/overview、project/list、project/page、project/{id}、task/list、risk/list、riskRule/list、riskRule/1、document/list、budget/list、workflow/category/list、workflow/definition/list）**分别发起不带任何 header 的 GET 请求** | 每条必须返回 HTTP 401/403 或业务 code=401/403；绝不允许出现 HTTP 200 + code=200 + 真实业务数据 | 若出现 1 条 HTTP 200 + code=200 → **高危缺陷**：未授权访问真实数据。安全门禁决策 = `stop`（AGENTS.md 要求立即停止所有专项） |
| 19 | SEC-JWT-001 | JWT | token 篡改 | P0 | 异常 | 1. 正常登录拿合法 token；2. 修改最后 1 字符（如把 'a' 改 'b'）；3. 访问 dashboard/overview | 返回 401/403；msg="认证失败/无效token"；无业务数据 | 通过失败即高危（签名校验未实现或被绕过） |
| 20 | SEC-JWT-002 | JWT | token 过期（如能构造） | P1 | 异常 | 1. 构造一个合法但已过期 7 天的 token（可从 expire_in=604800 = 7 天推算，或用历史保存的过期 token 复现）；2. 访问 dashboard/overview | 返回 401 + msg=token 已过期/认证过期 | 若 200 通过 → 中危缺陷：JWT 过期校验缺失 |
| 21 | SEC-JWT-003 | JWT | 多租户隔离：clientid header 换其他值 | P1 | 异常 | 1. 正确 token 不变；2. header `clientid: fakefakefakefakefakefakefakefak`（换另一个 clientId）；3. 访问 dashboard/overview | 返回 401/403（token 与 clientid 绑定校验）；如果 200 通过 → 证明只看 token 不看 header clientid，则"租户隔离检查缺失" | 若 200 通过 → 中危缺陷：多租户 clientid header 未校验（IPD 实际只有 1 租户但仍应校验一致性） |
| 22 | SEC-R4-001 | R4 合规 | 项目经理可见全员用户列表（含 admin 手机号、邮箱） | P0 合规 | 合规核查 | 1. 作为项目经理身份调用 `/system/user/list`；2. 检查返回 rows：列含 phonenumber（脱敏为"158****8888"？还是真实手机号"158XXXX8888"？）、email（a****@163.com 脱敏？还是 admin@xxx.com 真实邮箱？）；3. 记录结果并判定**合规性**（需要业务确认权限矩阵） | **合规判定标准（二选一必须明确）**：<br>✅ 如果"项目经理岗位允许查看全公司用户手机号/邮箱为真实值"→ 合规，不算缺陷（但仍要登记权限偏大作为知识库资产）<br>❌ 如果公司规定"项目经理只能查本人信息及直属下属"→ 不合规，**中高缺陷：水平越权暴露个人信息** | 此条不是直接技术判定，必须输出证据（返回字段样例）+ 合规结论 yes/no。若产品/研发未答复 = 系统报告登记"待确认"，缺陷不关闭 handoff 给产品确认。 |
| 23 | SEC-SQL-001 | SQL 注入 | project/page?projectName 单引号 payload | P1 | 异常注入 | 1. `GET /idmp/project/page?pageNum=1&pageSize=10&projectName=x' OR '1'='1`；2. 记录响应 code、msg、rows.length 与未注入 baseline 对比 | 结果 = code=200 且 rows.length ≤ 基线（不返回超量数据）；msg 不出现 "SQLException"、"MySQLSyntaxErrorException"、"ORA-" 等数据库关键字；rows.length 不能突然变成 500+ 条（绕过分页 = 注入成功） | 若出现堆栈 → 信息泄漏（中危）；若返回超量 500+ 条且 projectName 条件失效 → SQL 注入成功（高危） |
| 24 | SEC-SQL-002 | SQL 注入 | project/page?projectName 注释 payload | P1 | 注入 | `projectName=test' -- `（单引号+空格+双横注释） | 同上 | 同上 |
| 25 | SEC-SQL-003 | SQL 注入 | risk/list?description=OR 永真 | P1 | 注入 | `GET /idmp/risk/list?description=x' OR 1=1 --` | 同上：不返回超量；无 SQL 堆栈 | 同上 |
| 26 | SEC-SQL-004 | SQL 注入 | workflow/definition/list?flowName 盲注 sleep | P2 | 注入 | `flowName=x' AND SLEEP(3) --`（或 PG 的 pg_sleep）；记录实际响应耗时 vs baseline 耗时 | 响应耗时 ≤ 2× baseline（无额外 sleep 3 秒）；如果耗时 +3000ms 以上 → 时间盲注成功（高危） | 时间盲注高危（若触发） |
| 27 | SEC-SQL-005 | SQL 注入 | riskRule/1 id 参数整型注入 | P1 | 注入 | `GET /idmp/riskRule/1'`（非法数字后加单引号） | 500 msg 不出现堆栈；或 400 参数类型错误（类型安全是最佳实践） | 若出现 SQL 堆栈 → 中危信息泄漏 |
| 28 | SEC-XSS-001 | XSS | 风险描述字段 XSS（semi-auto，**不真正提交到数据库**，只看接口响应校验） | P2 | semi-auto 写操作 | 1. 使用 POST `/idmp/risk`（若存在该创建接口），body description = `<img src=x onerror=alert(1)>`；2. 如果返回 400 + msg="包含非法字符"/"不允许 HTML" 或对 < > & 做实体转义 → 算通过；3. 若返回 200 创建成功 → 再进入列表检查返回 description 字段是否 escape 成 `&lt;img src=x ...&gt;`（若后端 escape 也算通过） | **通过判定三选一**：<br>1) 创建接口 400（输入校验拦截 XSS payload）✅<br>2) 创建接口 200 但 description 被转义存储（escape）✅<br>3) 创建接口 200 + 查询时列表接口 response 中被 escape（前端不执行 onerror 即安全）✅<br>若创建 200 且返回值无 escape → **中危存储型 XSS（未实际影响，但存在潜在风险）** 登记缺陷。 |
