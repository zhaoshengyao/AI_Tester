# 评审重点
- 需求覆盖度是否充分：核心模块、页面流程、接口、协议/端云链路、业务实体、状态流转、异常场景、测试关注重点是否覆盖
- 测试范围一致性：测试方案中的范围是否都有用例，不测范围是否未混入正式用例
- 用例是否能追溯到需求分析报告和测试方案
- 用例表是否包含连续递增的“序号”列，且位于“用例编号”前
- 是否有遗漏
- 是否有重复
- 是否不可执行
- 预期是否不明确
- 自动化标记是否合理
- 自动化结论是否具备执行层级：smoke、readonly-regression、semi-auto、write-regression、protocol-cloud、performance、security、manual、blocked
- 自动化候选是否已有覆盖矩阵占位，未实现项是否明确写“未实现”
- 跨专项一致性是否合理：字段、状态、权限、错误表现、设备身份、数据链路是否冲突
- 接口用例是否区分实测接口基线、文档差异核对、已确认契约断言；未确认接口文档契约不得作为硬预期
- 嵌入式第一版是否只覆盖 protocol-cloud，不得混入固件、硬件、OTA、HIL、串口日志

# 需求覆盖度评审
| 需求分析来源 | 覆盖检查 |
|--------------|----------|
| 功能模块拆解 | 每个核心模块至少有功能用例；涉及接口的模块还应有接口用例 |
| 页面与交互流程 | 主要页面、入口、流程、弹窗、状态展示是否有功能用例 |
| 接口与数据交互 | 核心接口、实际观察接口、接口待确认项是否有接口用例或待确认记录 |
| 协议/端云联调 | 协议入口、设备身份、上报样例、API 查询、UI 展示是否有嵌入式用例 |
| 业务实体与关键字段 | 核心实体、关键字段、筛选、详情、状态字段是否覆盖 |
| 状态流转与业务规则 | 核心状态变化、权限规则、异常规则是否覆盖 |
| 异常场景与边界行为 | 空数据、非法输入、接口失败、未授权、未知设备等是否覆盖 |
| 测试关注重点 | 需求分析报告中的测试关注重点必须至少有 P0/P1 用例覆盖 |

# 覆盖结论
| 结论 | 判定 |
|------|------|
| 已覆盖 | 有明确正式用例覆盖 |
| 部分覆盖 | 只有部分场景覆盖，边界或异常缺失 |
| 待确认覆盖 | 需求/接口/协议/数据未确认，无法生成完整用例 |
| 未覆盖 | 没有正式用例，也没有待确认说明 |
| 不纳入本轮 | 测试方案明确列为不测范围，并说明原因 |

# 评审问题分级
| 级别 | 含义 | 阶段影响 |
|------|------|----------|
| P0 | 核心需求未覆盖、用例不可执行、评审版缺失、字段缺失严重 | 不通过 |
| P1 | 自动化层级错误、写操作无回滚、接口预期不可断言、关键异常缺失 | 有条件通过或不通过 |
| P2 | 重复用例、标题不清、步骤不够细、优先级不合理 | 可有条件通过 |
| P3 | 轻微格式或表达问题 | 可通过并记录 |

# 评审版变更留痕
评审版相对原始用例的变化必须记录：
- 新增：补充遗漏用例
- 修改：修正步骤、预期、优先级、自动化结论、执行层级
- 合并：合并重复或高度相似用例
- 删除：删除不在范围、重复、不可执行或错误用例
- 标记阻塞：条件不足，暂不进入执行
- 标记后续：属于后续范围，不纳入本轮

删除、合并、新增、修改自动化结论或执行层级时，必须写明原因。

# 评审结论
| 结论 | 判定 |
|------|------|
| 通过 | 需求覆盖完整，问题仅为轻微格式或已修正 |
| 有条件通过 | 存在待确认、部分覆盖或局部阻塞，但不影响进入覆盖矩阵；必须说明限制 |
| 不通过 | 核心需求未覆盖、用例不可执行、范围混乱、字段缺失或自动化层级严重错误 |

有条件通过必须写明：
- 哪些范围可以进入覆盖矩阵。
- 哪些范围只能待确认或 blocked。
- 哪些专项不能进入自动化。

# 评审记录必须包含
- 评审结论：通过 / 有条件通过 / 不通过
- 需求覆盖度评审
- 需求覆盖统计：总数、已覆盖、部分覆盖、待确认覆盖、未覆盖、不纳入本轮
- 专项评审结果
- 问题清单及 P0/P1/P2/P3 分级
- 评审版变更记录
- 自动化结论与执行层级评审
- 跨专项一致性评审
- 风险与待确认项
- 下一步建议

# 强制规则
- 以找问题为主，不以润色为主
- 需求覆盖度是第一优先级，禁止只做格式润色
- 需求覆盖缺失时不得输出“通过”
- 未通过评审不得进入自动化执行
- 评审记录必须写明通过 / 不通过 / 有条件通过
- 评审记录必须输出需求覆盖统计和评审版变更记录
- 删除、合并、新增用例不得静默处理，必须记录原因
- 跨专项字段、状态、权限、协议口径冲突必须记录
- 评审接口用例时必须优先检查预期来源；真实接口可访问时，实测接口基线优先于接口文档
- 有接口文档但与真实接口不一致时，未确认差异只能标记为“差异核对/待确认”，不得评审通过为 smoke 硬断言
- 没有接口文档时，接口用例必须追溯到实测接口基线，不得出现“按接口文档应返回”类预期
- 自动化前置条件必须明确列出；不满足时必须写“待确认”
- 评审版用例不得只写“自动化/不自动化”，必须说明执行层级或阻塞原因
- 写操作没有回滚策略却标记自动化，不通过
- JMeter/ZAP 未满足门禁却标记可执行，不通过
- 嵌入式后续范围标记为自动化，不通过
- 评审结论为通过或有条件通过，才可进入覆盖矩阵
- 输出必须按顺序包含：当前阶段、输入文件、产出文件、正文/核心内容、执行结论、风险与待确认项、下一步建议。正文/核心内容必须位于执行结论、风险与待确认项、下一步建议之前；执行结论、风险与待确认项、下一步建议必须作为文档收尾部分
