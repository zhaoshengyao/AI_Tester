# 目标
生成可进入测试设计阶段的正式需求分析报告。

需求分析阶段只回答：
1. 系统现在是什么样。
2. 系统看起来要解决什么业务问题。
3. 后续测试设计需要重点关注什么风险、规则、流程、数据和接口。

# 输入
- `docs/AI执行最小规则.md`
- 项目地址、账号、密码
- `docs/requirements/`
- `docs/prototype/`
- `docs/api/`
- `docs/embedded/`
- `docs/protocol/`
- `docs/device/`
- `docs/knowledge/README.md`（历史知识索引，默认先读）
- `docs/knowledge/`（仅在索引提示相关或确属迭代/回归场景时按需展开）

# 输出
- docs/analysis/需求分析报告.md

# 工作流
1. 判断输入模式：只有项目地址、只有文档、项目地址 + 文档。
2. 如果 `docs/knowledge/README.md` 存在，先读取索引，判断当前是否真需要展开历史知识文件。
3. 只有在以下场景才按需展开具体知识文件：当前任务明确是产品迭代/修复后回归；索引提示存在直接相关的历史缺陷/回归资产；需求或接口与历史条目明显冲突需要比对。
4. 记录实际输入来源、已读文件、已访问页面和已观察接口。
5. 按输入模式确定分析依据优先级。
6. 只有项目地址时，按黑盒探索方式分析实际系统可观察行为。
7. 只有文档时，按文档优先级处理冲突。
8. 项目地址 + 文档时，以实际实现为最高优先级，并记录文档与实现差异；接口文档只作为对照依据，不覆盖真实接口行为。
9. 拆解系统概览、功能模块、页面流程、接口数据、协议/端云联调、业务实体、状态流转、异常边界。
10. 识别历史知识对本轮需求的影响，区分仍有效、待确认、已过期风险。
11. 只重点列出需求待确认和接口待确认。
12. 输出测试关注重点，供测试方案阶段继承。
13. 生成正式报告。

# AI 读取优化
- 默认先读取 `docs/AI执行最小规则.md` 和 `docs/knowledge/README.md`，再决定是否展开其他资料。
- 默认只读取 `docs/knowledge/README.md`，不默认整包读取 `docs/knowledge/*.md`。
- 历史知识只用于回答“这轮是否值得参考过去经验”，不是默认主上下文。
- 已经能从当前项目地址、当前文档和当前接口观察得到的信息，不再回头用历史知识重复确认。
- 需求分析阶段不回读后续长文档，例如系统测试报告、知识库正文或历史批次归档，除非当前任务明确是迭代差异分析。

# 输入模式与优先级

| 输入模式 | 优先级 |
|----------|--------|
| 只有项目地址 | 实际系统可观察行为 > 页面 DOM/路由/菜单/按钮/弹窗/提示 > 浏览器网络请求和响应 > 接口实际返回结构 > 页面错误/控制台错误 |
| 只有文档 | 原型与页面说明 > 接口文档 > 协议文档 > 需求文档中的业务背景和意图 |
| 项目地址 + 文档 | 实际系统实现方式 > 实际接口请求/响应 > 原型与页面说明 > 接口文档 > 协议文档 > 需求文档中的业务背景和意图 |

# 只有项目地址时的探索顺序
1. 启动前检查：被测地址、账号密码、登录状态、页面标题、路由、明显控制台错误。
2. 页面探索：登录页、首页/大盘、菜单结构、核心列表页、详情页/弹窗、写操作入口、日志/审计/记录、端云联调入口。
3. 接口观察：登录接口、当前用户接口、首页数据接口、核心列表接口、详情接口、操作接口、端云相关接口。
4. 写操作只记录入口、请求形态和校验表现，不默认提交真实数据。
5. 无法观察的业务意图标记为需求待确认；无法确认的接口契约标记为接口待确认。

# 有文档时的读取顺序
1. 列出实际读取的文件。
2. 先读原型/页面说明，建立页面和流程骨架。
3. 再读接口文档，建立接口和数据骨架。
4. 再读协议文档，建立端云联调骨架。
5. 最后读需求文档，补充业务目标、角色、规则和背景。

# 冲突处理
- 只有文档时，冲突优先级为：原型 > 接口文档 > 协议文档。
- 有项目地址和文档时，以实际实现写主分析结论，文档差异单独记录。
- 有真实接口可访问时，接口分析以真实请求、响应状态码、响应字段、鉴权方式、分页/筛选/错误响应为主；接口文档不一致处写入“文档与实际实现差异”，不得用文档覆盖实际行为。
- 没有接口文档时，必须输出“实测接口基线”，列出接口来源、请求方法、路径、触发页面/操作、请求参数、响应结构、鉴权观察和待确认项。
- 有接口文档但实际接口不一致时，报告应同时写“实测行为”和“文档描述”，并标记待确认；只有产品/研发确认文档契约后，后续测试才按文档契约判定失败。
- 原型与接口字段不一致时，页面分析按原型写，接口分析按接口写，差异记录。
- 只有文档、没有真实接口可观察时，接口文档与协议文档字段不一致按“平台接口参考接口文档、端云协议参考协议文档”记录，并标记差异；一旦真实接口可访问，平台接口以实测行为为准。
- 需求描述与原型流程不一致时，流程按原型写，业务意图按需求写，差异记录。

# 报告结构
1. 当前阶段
2. 输入文件与输入来源
3. 产出文件
4. 实际读取/访问记录
5. 分析依据优先级
6. 历史知识引用与有效性判断
7. 系统概览
8. 功能模块拆解
9. 页面与交互流程拆解
10. 接口与数据交互初步分析
11. 协议/端云联调初步分析
12. 业务实体与关键字段
13. 状态流转与业务规则
14. 异常场景与边界行为
15. 文档与实际实现差异
16. 待确认项
17. 测试关注重点
18. 执行结论
19. 风险与待确认项
20. 下一步建议

# 待确认项
需求分析阶段只重点维护两类待确认：
- 需求待确认：业务规则、角色权限、流程意图、状态定义、边界规则、异常处理意图。
- 接口待确认：接口契约、字段含义、业务码、鉴权方式、错误码、分页/筛选/排序规则。

其他信息能通过实际系统观察补齐的，应主动补充，不要让用户重复提供。

# 完成判定
满足以下条件后，即可进入测试设计阶段：
- 已说明输入模式和分析依据优先级。
- 已列出实际读取文件或实际访问页面/接口。
- 已完成核心模块拆解。
- 有接口文档或实际请求时，已完成接口初步分析。
- 有协议资料、设备入口或上报链路时，已完成协议/端云联调初步分析。
- 已单独列出需求待确认和接口待确认。
- 已输出测试关注重点。

待确认项不阻塞进入测试设计阶段，但必须带入测试方案和测试计划。

# 强制规则
- 需求分析阶段不输出测试范围和不测范围。
- 未访问项目且未读取文档前不得输出确定性结论。
- 只有项目地址时，分析结论只能代表实际可观察行为，不得等同于产品原始需求。
- 不确定必须标记待确认，不得脑补业务规则、协议字段或接口契约。
- 输入目录为空但提供了项目地址时，仍可基于实际系统观察生成需求分析报告。
- `docs/knowledge/` 中的历史知识只能作为参考；与当前实际实现或新文档冲突时，按当前优先级处理，并标记历史知识已过期风险或待确认。
- 不得把 `docs/knowledge/` 全目录扫描作为默认动作；必须先读索引，再按需展开具体文件。
- 项目地址不可达且没有文档时，报告必须写“未执行”和“待确认”，不得进入测试设计。
- 不生成测试用例，不生成自动化脚本，不执行测试。
- 不执行破坏性写操作来探索需求。
- 输出必须按顺序包含：当前阶段、输入文件、产出文件、正文/核心内容、执行结论、风险与待确认项、下一步建议。正文/核心内容必须位于执行结论、风险与待确认项、下一步建议之前；执行结论、风险与待确认项、下一步建议必须作为文档收尾部分
