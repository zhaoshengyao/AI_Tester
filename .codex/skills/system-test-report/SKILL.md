# 工作流
1. 优先读取本轮 `docs/test-runs/YYYYMMDD-HHMMSS/批次摘要.md`；若不存在，再回退到专项报告、覆盖矩阵和缺陷清单。
1.1 同时读取本轮 `stage-status`，优先用统一状态判断哪些专项已完成、未执行或需更新，再决定是否继续追证。
2. 读取需求分析报告、测试方案、测试计划和评审记录，但只提取系统报告必需字段，不重复抄写上游正文。
3. 读取 API、UI、嵌入式、性能、安全专项报告的最新正式结论。
4. 读取 API、UI、嵌入式覆盖矩阵，统计计划、实现、执行、阻塞和未实现情况。
5. 读取各专项缺陷清单，按严重级别、来源专项、影响范围、状态和上线影响汇总。
6. 对缺失报告、缺失矩阵或未执行专项写“未执行/待确认”，不得补造结果。
7. 只有在以下场景才展开原始结果目录和 run logs：需要补证据索引；报告统计冲突；专项报告未写清关键结果。
8. 校验覆盖矩阵、执行报告和缺陷清单之间的一致性；冲突必须列入待确认。
9. 记录测试批次、被测版本、环境快照、工具版本、账号角色和数据策略；缺失时写“待确认”。
10. 汇总各专项冒烟结论、结果分析和“下一步决策”；缺失决策时写“待确认”，不得替专项补决策。
11. 归并各专项的 continue/retest/collect-evidence/downgrade/stop/handoff 状态，输出全局阶段建议和依赖关系。
12. 汇总复测与回归状态；非复测批次也要明确说明。
13. 汇总文档与实际接口差异，区分实测行为、文档描述、是否已确认以文档为准、当前报告处理方式和待确认项。
14. 结合阻塞缺陷、未执行专项、待确认项、统计冲突、证据完整性、专项下一步决策和遗留风险给出最终建议。
15. 系统测试报告以“全局判断、证据索引、跨专项一致性和上线建议”为主；当前批次的基础统计与事实快照优先引用 `批次摘要.md`，不整段重写。
16. 只提炼对后续复用有价值的流程经验和配置改进建议，避免在系统报告中重复展开知识库正文。
17. 执行报告质量自检，决定闭环状态。

# AI 读取优化
- 默认输入顺序：批次摘要 -> 覆盖矩阵 -> 专项报告 -> 缺陷清单 -> 原始结果。
- 不把 `docs/reports/`、`docs/defects/`、`tests/*/reports/` 的整目录扫描作为默认动作。
- 已经能从覆盖矩阵和专项报告得到的数字，不再通过 raw 报告重复计算。
- 只有出现“统计冲突、证据缺失、专项报告不完整”时，才展开 HTML/JUnit/JTL/trace。
- `系统测试报告阶段细化方案.md` 属于参考资料，不作为默认输入。
- 已在 `批次摘要.md` 中稳定表达的当前批次事实，系统报告应以引用和归并为主，不再逐项重复铺陈。

# 覆盖与执行统计
| 指标 | 要求 |
|------|------|
| 需求覆盖率 | 以需求分析报告和评审版用例为依据，区分已覆盖、部分覆盖、待确认覆盖、未覆盖 |
| 用例执行率 | 已执行用例 / 计划执行用例 |
| 自动化实现率 | 已实现自动化用例 / 自动化候选用例 |
| 自动化执行率 | 已执行自动化用例 / 已实现自动化用例 |
| 通过率 | 通过用例 / 已执行用例 |
| 阻塞率 | 阻塞用例 / 计划执行用例 |
| 缺陷分布 | 按专项、模块、严重级别、状态统计 |

# 专项汇总规则
- API 自动化必须汇总 `docs/reports/API自动化覆盖矩阵.md`、`docs/reports/接口自动化测试报告.md` 和 `docs/defects/接口缺陷清单.md`。
- UI 自动化必须汇总 `docs/reports/UI自动化覆盖矩阵.md`、`docs/reports/UI自动化测试报告.md`、`docs/reports/UI兼容性测试报告.md` 和 `docs/defects/UI缺陷清单.md`。
- 嵌入式第一版必须汇总 `docs/reports/嵌入式覆盖矩阵.md`、`docs/reports/嵌入式协议端云联调测试报告.md` 和 `docs/defects/嵌入式缺陷清单.md`；只代表 protocol-cloud 范围。
- 性能测试必须汇总 `docs/reports/性能测试报告.md` 和 `docs/defects/性能缺陷清单.md`，并写明 JMeter 原始结果路径。
- 安全测试必须汇总 `docs/reports/安全测试报告.md` 和 `docs/defects/安全缺陷清单.md`，并写明 ZAP 原始报告路径。
- 缺陷清单文件不存在时写“缺陷清单未生成”；文件存在且无缺陷时才写“未发现缺陷”。

# 证据索引规则
- 每个关键统计必须能追溯到专项报告、覆盖矩阵、缺陷清单或原始结果路径。
- 本轮已存在 `批次摘要.md` 时，优先把它作为证据入口索引，而不是直接展开整个批次目录。
- 必须汇总 `docs/reports/run-logs/` 中的执行命令、执行时间、退出码或失败原因。
- API 原始结果优先引用 `tests/api/reports/`。
- UI 原始结果优先引用 `tests/ui/reports/` 中的 trace、截图、video、HTML 报告。
- 嵌入式原始结果优先引用 `tests/embedded/reports/` 中的协议包、平台查询、接口响应、日志或截图。
- 性能原始结果优先引用 `tests/performance/results/` 中的 JTL、dashboard、JMeter log。
- 安全原始结果优先引用 `tests/security/reports/` 中的 ZAP HTML/JSON/XML 报告。
- 没有原始结果路径时必须写“证据不完整”，不得省略。

# 环境与批次规则
- 必须记录测试批次、被测版本、被测地址、环境名称、执行时间、账号角色、工具版本和数据策略。
- 账号只写用户名和角色，不得明文暴露密码。
- token、cookie、session、密钥、可复用认证头必须脱敏。
- 缺少被测版本、构建号或部署时间时，写“待确认”，最终结论不得描述为生产等价验证。

# 一致性规则
- 覆盖矩阵与执行报告数量不一致时，写“统计冲突”，列出差异，不得自行取值覆盖。
- 执行报告存在失败但缺陷清单没有登记时，写“缺陷登记缺失”并列为待确认。
- 执行类专项报告缺少“下一步决策”时，系统测试报告必须标记“专项决策缺失”，不得擅自补成 continue。
- 缺陷清单存在严重缺陷但上线建议为建议上线时，必须有豁免说明；否则结论只能是不建议上线或暂无法判断。
- 同一指标在多个报告中不一致时，列入“报告一致性问题”。
- 执行结果优先使用专项执行报告；覆盖范围优先使用覆盖矩阵；缺陷状态优先使用缺陷清单。三者冲突时不得合并为通过。
- 只要真实接口可访问，接口结论优先依据实测行为和已确认业务规则；接口文档只作为差异对照来源。
- 接口文档与真实接口不一致时，必须列入“文档与实际接口差异/待确认”；未确认以文档为准前，不得直接合并为产品缺陷或 smoke 阻断。
- API 自动化若把未确认文档契约作为硬断言导致失败，系统报告应标记为“断言口径待确认/自动化维护项”，并与真实接口失败分开。

# 专项下一步决策汇总规则
| 专项状态 | 系统报告动作 |
|----------|--------------|
| continue | 说明可以继续的后续专项、前置条件和证据依据 |
| retest | 写明需复测范围、触发条件、复测前准备和是否阻塞后续阶段 |
| collect-evidence | 写明缺失证据、责任边界、补充方式和补齐前不得继续的范围 |
| downgrade | 写明降级后的执行边界、未执行范围和对整体结论的影响 |
| stop | 写明停止原因、被阻断阶段和恢复条件 |
| handoff | 写明移交对象、移交证据、影响范围和接回复测条件 |

# 流程复用与配置改进建议
- 必须总结哪些门禁、冒烟脚本、证据采集动作和决策规则可直接复用于下一项目或下一环境。
- 必须记录本轮暴露出的配置缺口，例如缺日志、缺监控、缺账号角色、缺基线阈值、缺归档字段。
- 必须给 knowledge-base 阶段提供“如何做/为什么这样做/下次怎么复用”的输入，不得只沉淀结果摘要。

# 缺陷闭环与复测规则
- 缺陷状态必须区分：新建/待确认、已修复待复测、已验证关闭、延期/豁免、无法复现。
- 延期或豁免缺陷必须写明原因、责任人、截止时间或适用范围；缺失时写“待确认”。
- 修复后复测批次必须写明复测缺陷、修复版本、复测结果、回归范围和未复测原因。
- 非复测批次必须写“本轮非复测批次”或“待确认”。
- 存在 Blocker/Critical/High 安全风险、认证授权绕过、数据泄露、核心流程不可用或严重性能不可用时，除非有明确豁免，否则不得建议上线。

# 最终结论规则
| 结论 | 允许条件 |
|------|----------|
| 建议上线 | 阻断/严重缺陷均关闭或有明确豁免；核心需求已覆盖；关键自动化和专项无阻塞风险 |
| 有条件上线 | 存在非阻断缺陷或部分专项未执行，但影响范围明确且有补救计划 |
| 不建议上线 | 存在阻断缺陷、核心需求未覆盖、关键环境不可用、关键专项未执行且风险不可接受 |
| 暂无法判断 | 输入报告缺失、执行证据不足、关键待确认项未关闭 |

接口文档与实际接口差异必须单独判断：已确认以文档为准的差异可纳入产品缺陷；未确认差异只能纳入待确认、契约澄清或自动化断言口径问题，不得单独作为不建议上线依据。

# 闭环状态
| 状态 | 含义 |
|------|------|
| full-flow-completed | 所有计划专项均已执行并生成报告，缺陷和风险已汇总 |
| flow-closed-with-exceptions | 有专项未执行或部分阻塞，但原因、影响和后续动作已写清 |
| flow-blocked | 关键前置门禁失败，后续专项无法执行，必须停止并等待恢复 |
| report-insufficient | 产出文件缺失或证据不足，无法形成系统测试结论 |

# 报告质量自检
| 自检项 | 通过标准 |
|--------|----------|
| 文件完整性 | 所有计划专项要么有报告，要么有未执行原因 |
| 证据完整性 | 关键统计有来源文件或原始结果路径 |
| 统计一致性 | 覆盖矩阵、执行报告、缺陷清单不存在未解释冲突 |
| 决策完整性 | 执行类专项都有冒烟后结论和下一步决策，缺失项已标记待确认 |
| 风险完整性 | 未执行、阻塞、待确认、严重缺陷均进入风险区 |
| 结论合理性 | 上线建议与缺陷状态、执行覆盖、未执行项一致 |
| 信息安全 | 报告中不明文暴露密码、token、cookie、敏感业务数据 |

# 下一阶段衔接
- 系统测试报告生成后，必须进入 `knowledge-base` 阶段沉淀测试知识资产。
- 下一步建议中必须说明哪些内容应进入 `docs/knowledge/`，例如回归资产、缺陷模式、自动化维护项、环境工具问题和下一轮迭代建议。
- 系统测试报告不直接改写知识库，只提供可沉淀的依据和证据索引。

# 强制规则
- 只汇总已存在报告和缺陷清单，不得补造未执行阶段的结果
- 不得默认整包读取历史批次归档；除非当前批次证据不足或存在跨批次比对需求。
- 必须汇总 API/UI/嵌入式覆盖矩阵，明确总用例数、已实现自动化数、已执行数、未实现数、阻塞数
- 缺失的专项报告必须写“未执行”
- 不得把第一版嵌入式 protocol-cloud 写成完整嵌入式测试完成
- 不得把缺陷清单缺失写成未发现缺陷
- 不得把未确认的接口文档契约当成真实接口失败；真实接口可访问时必须单列文档与实际接口差异
- 不得在报告中明文暴露密码、token、cookie 或可复用会话信息
- 不得在统计冲突未解释时给出确定性通过结论
- 上线建议必须基于已执行结果、缺陷状态和遗留风险
- 任一报告质量自检项不通过时，闭环状态不得写 `full-flow-completed`
- 输出必须按顺序包含：当前阶段、输入文件、产出文件、正文/核心内容、执行结论、风险与待确认项、下一步建议。正文/核心内容必须位于执行结论、风险与待确认项、下一步建议之前；执行结论、风险与待确认项、下一步建议必须作为文档收尾部分
